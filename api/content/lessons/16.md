title: 読みやすいコードと責務の分け方
---

## このレッスンの目標

自分が書いたコードでも、1週間後には「これは何をしているんだっけ？」となります。読みやすいコードとは、次に読む人が目的や変更する場所を見つけやすいコードです。短いことや、難しい書き方を使うことが目標ではありません。

このレッスンでは、**すでに動くコードを、動きを変えずに整理する**練習をします。これを「リファクタリング」と呼びます。クラスとオブジェクトの後に取り組みます。例外処理やデザインパターンの知識は不要です。

全5問です。初めてなら1問ずつ、各15〜20分を目安に進めましょう。先にすべての用語を覚える必要はありません。資料の後半は、慣れてから読み返しても大丈夫です。

## 進め方：一度に全部変えない

1. 元のコードを実行する。引数と表示結果を確認する。
2. 問題文の仕様を読む。「何を変えずに残すか」を確認する。
3. 名前だけ、条件だけ、メソッド1つだけ、という小さな単位で変更する。
4. 実行・採点で、以前と同じ結果になるかを確かめる。
5. 変更の理由を自分の言葉で説明してから提出する。

**最初のコードでも自動採点は通ります。テスト合格だけでは、この演習の改善は完成していません。** 自動採点は表示結果を確認します。名前・責務・コメントなどは担当者がレビューします。このレッスンではフロー図の提出は不要です。

## 問1につながる：名前から意味を伝える

```java
// 読む人が p と n の意味を推測する必要がある
int p = 800;
int n = 3;
int x = p * n;

// 何の値で、単位が何かを名前で伝える
int unitPriceYen = 800;
int quantity = 3;
int subtotalYen = unitPriceYen * quantity;
```

`data`、`tmp`、`result` が必ず悪いわけではありません。ただし「どんなデータか」「何の結果か」が分からない場所では具体的にします。`price` より `unitPriceYen` なら、単価なのか合計なのか、円なのかが分かります。短いループの `i` まで長い名前に変える必要はありません。

真偽値には `isActive`、`hasPermission`、`canRegister` など、質問として読める名前を付けると条件を追いやすくなります。`isNotDisabled` のような二重否定は、可能なら肯定形にします。名前を変えるときは、使っている場所も一緒に変更します。

## 問2につながる：早期リターンで入れ子を浅くする

入れ子とは、`if` の中にさらに `if` がある状態です。先に「ここから先に進めない場合」を扱うと、通常の処理を追いやすくできます。

```java
static String registrationMessage(int age, boolean hasConsent) {
    if (age < 0) {
        return "入力エラー";
    }
    if (age < 18 && !hasConsent) {
        return "同意が必要";
    }
    return "登録できます";
}
```

`return` は、今実行しているメソッドをその場で終え、値を呼び出した場所に返します。上の例では18歳以上なら同意の有無に関係なく登録できます。条件の順番を変えると結果が変わることがあるので、境界の年齢も確認します。

早期リターンを増やすこと自体が目的ではありません。単純な二択なら `if / else` のままで十分です。終了前に必要な処理がある場合は、それを飛ばしていないかも確認します。

## 問3につながる：責務とは「何を受け持つか」

料理で、注文を受ける・料理を作る・伝票を書く、という役割があるように、コードにも役割があります。「責務」は、そのメソッドやクラスが受け持つ仕事のことです。

例えば `main` が入力の読み取り、商品代金の計算、送料の決定、表示を全部行うと、送料を直したいだけでも長い処理を読む必要があります。

```java
int subtotalYen = calculateSubtotal(unitPriceYen, quantity);
int shippingFeeYen = calculateShippingFee(subtotalYen);
System.out.println(formatReceipt(subtotalYen, shippingFeeYen));
```

計算するメソッドは値を返し、表示は呼び出し側で行うと、同じ計算を別の画面でも使いやすくなります。メソッドの名前から中身が想像できるかを確認しましょう。1行ずつすべて別メソッドにする必要はありません。

## 問4につながる：神クラスを避ける

「神クラス」は、いろいろな仕事を1つで抱え込むクラスの俗称です。例えば `ShopManager` に、会員管理、注文計算、在庫更新、メール送信、画面表示が全部ある状態です。

困るのは行数そのものより、**別々の理由で変更される処理が集まること**です。メールの文面変更でも価格計算の修正でも同じクラスを触るため、影響を確かめにくくなります。

まずは、注文のデータと計算を `Order`、表示する文章を作る処理を `ReceiptFormatter` に分けてみます。計算を変えるときと、文章を変えるときに触る場所が分かれます。

演習で出てくる `private` は「そのクラスの中からだけ使える」という指定です。`final` をフィールドに付けると、最初に設定した値を後から代入し直せません。例えば `private final int quantity;` は、注文の個数を外から直接書き換えられないようにします。ただし、`final` を付けたオブジェクトの内部まで自動的に変更禁止になるわけではありません。

名前だけ `OrderUtil` や `CommonManager` に変えたり、すべてを別の巨大クラスへ移したりしても解決にはなりません。一方、この小さな演習でメール送信や在庫管理まで新設する必要もありません。実際に存在する役割から分けます。

## 問5につながる：他のオブジェクトの中身をたどりすぎない

```java
// 呼び出し側が User → Profile → Address の構造を知っている
String city = user.getProfile().getAddress().getCity();

// 必要な情報を、適切な窓口に頼む
String city = user.getShippingCity();
```

前者では、住所の置き場所が変わると利用側も修正が必要になります。このような、別々のオブジェクトを次々にたどるコードを「メッセージチェーン」と呼びます。内部のつながりを知りすぎず、必要な情報や処理をオブジェクトに頼む考え方は、発展的には「デメテルの法則」と関係します。

**ドットが何個あるかだけで判断しません。** `new StringBuilder().append("合計: ").append(totalYen).toString()` のように、同じ組み立て用オブジェクトを操作するAPIや、意図が分かるStreamの連続処理は、長いからという理由だけで分解する必要はありません。

また、変数に分けて `Profile p = user.getProfile(); Address a = p.getAddress();` と書くだけでは、内部構造への依存は残ります。必要な窓口を考えましょう。ただし、すべてのgetterを無条件に中継する巨大な窓口を作るのも避けます。自分で制御できない外部ライブラリの場合は、利用箇所をまとめる方法もあります。

## コメントは「なぜ」を補う

```java
// 悪い例：コードを日本語に言い換えただけ
quantity++; // quantity に1を足す

// 役立つ例：コードだけでは分からない業務上の理由
// 梱包をまとめられる注文は、商品代金3000円以上で送料を店舗負担にする。
```

コメントは不要という意味ではありません。背景・制約・外部仕様・注意点を説明すると役立ちます。メソッドの使い方を伝える説明も必要です。ただし、古いコメントが実際の動作と食い違うと読む人を迷わせます。コード変更時に見直しましょう。使わなくなったコードを大量にコメントアウトして残すより、履歴管理を使います。

## よくあるアンチパターンの見つけ方

アンチパターンとは、つい選びがちだけれど、後から読みにくさや変更の難しさにつながる書き方です。以下は絶対禁止の一覧ではなく、見直すきっかけです。

| よくある書き方 | 困りやすいこと | 最初に試す改善 |
| --- | --- | --- |
| `a`、`data`、`tmp2` ばかり | 値の意味を毎回調べる | 目的や単位を名前にする |
| 深い `if` の入れ子 | 正常に進む道筋を追いにくい | 進めない条件を先に返す |
| `!isNotDisabled` など二重否定 | 頭の中で何度も反転する | 肯定形に名前を付ける |
| 長い条件を何度も書く | 意味や修正箇所を見失う | `canRegister` などの判定に名前を付ける |
| `3000`、`500` が各所に登場 | 数字の意味と変更対象が不明 | 仕様の値に定数名を付ける |
| 似た計算をコピペする | 一方だけ直して結果がずれる | 同じルールなら計算を1か所にする |
| 何でも入った神クラス | 無関係な修正が集中する | 変更する理由が違う仕事を分ける |
| `CommonUtil` が何でも屋になる | 必要な処理を探せない | 注文・料金など対象を具体化する |
| 計算する名前なのに中で表示する | 呼ぶだけで予想外の操作が起きる | 計算結果を返し、表示を分ける |
| `getA().getB().getC()` | 相手の内部構造に強く依存する | 必要な情報を適切な窓口へ頼む |
| `process(true, false)` | 真偽値の意味が呼び出し側で不明 | 目的別のメソッドや、意味のある値を検討 |
| 関係のない値までフィールドにする | 誰がいつ変更したか追いにくい | その処理だけの値はローカル変数にする |
| フィールドをすべて公開する | どこでも値を変えられルールを守りにくい | 非公開にして必要な操作を提供する |
| コメントと実際の条件が違う | 誤った理解で修正する | 仕様を確認しコメントも更新する |
| コードの言い換えコメントが大量 | 大事な背景説明が埋もれる | 意図・制約を説明する |
| 1行に処理を詰め込む | 途中の計算や失敗箇所が不明 | 意味のまとまりで行と変数を分ける |
| 何でも1行メソッドに分割 | 読むたびにあちこち飛ぶ | 名前で意図が伝わるまとまりにする |
| 似ているだけで何でも共通化 | 別々の仕様変更に対応しにくい | 同じルールか確認してからまとめる |
| 使わない将来用のクラスを大量に作る | 学ぶ量と修正箇所が増える | 今ある要件で必要な構造にする |
| リファクタリング中に仕様も変える | 不具合か改善か判定しにくい | 構造の変更と仕様の変更を別に進める |

## レビューで説明してみよう

- どこが読みにくかった？ 名前・条件・責務・依存のどれが原因だった？
- 何を変えて、次に読む人が何を推測しなくてよくなった？
- 計算ルールを変えるならどのメソッド？ 表示を変えるならどこ？
- 元と同じ出力になることを、どんな入力で確かめた？
- 分割や中継を増やしすぎて、かえって追いにくくしていない？

## Option：慣れてきたら考えること

「1クラスは何行まで」「ドットは2つまで」という数だけのルールでは、適切な設計を判断できません。変更するときに何か所を理解する必要があるか、利用する側に余計な知識を要求していないかを見ます。単一責任の原則、カプセル化、凝集度と結合度は、この考え方を深めるための言葉です。

初回は用語の暗記より、今回の変更を具体例で説明できれば十分です。
