## テスト仕様書とは

「何を、どんな手順で、どんなデータでテストし、どうなれば合格か」をまとめた文書です。テストを始める **前に** 作ります。

- 誰が実施しても同じテストができる
- テストの漏れや重複に気づける
- 何をテストしたかの記録・証拠になる

## 書く項目

| 項目 | 内容 |
|---|---|
| テスト ID | 一意の番号（例: UT-LOGIN-001） |
| テスト対象 | 機能、画面、メソッド |
| テスト観点 | 何を確かめるか（正常系、異常系、境界値など） |
| 前提条件 | テスト前の状態（ログイン済み、データが 3 件ある など） |
| 手順 | 操作の順番 |
| 入力データ | 具体的な値 |
| 期待結果 | 合格となる結果。具体的に書く |
| 実施結果 | OK / NG、実施日、実施者 |
| 備考 | NG のときの不具合番号など |

## 例: ログイン機能

| ID | 観点 | 前提条件 | 入力 | 期待結果 |
|---|---|---|---|---|
| UT-LOGIN-001 | 正常系 | 社員番号 T001 が登録済み | T001 / 正しいパスワード | ホーム画面に移る |
| UT-LOGIN-002 | 異常系 | 同上 | T001 / 誤ったパスワード | 「社員番号またはパスワードが正しくありません」と表示し、ログイン画面のまま |
| UT-LOGIN-003 | 異常系 | — | 未登録の T999 / 任意 | UT-LOGIN-002 と同じメッセージ |
| UT-LOGIN-004 | 入力チェック | — | 社員番号を空欄 | 「社員番号を入力してください」と表示 |
| UT-LOGIN-005 | 境界値 | 同じ社員番号で 5 回失敗済み | T001 / 誤ったパスワード | 「試行回数が多すぎます」と表示 |

## 期待結果の書き方

あいまいな書き方では、合否を判断できません。

| あいまいな例 | 具体的な例 |
|---|---|
| 正しく表示される | 一覧に 3 件、登録日の新しい順に表示される |
| エラーになる | 「金額は 1 以上を入力してください」と赤字で表示され、保存されない |
| 速い | 3 秒以内に結果が表示される |

## 観点の洗い出し

- **正常系**: 想定どおりの入力・操作
- **異常系**: 誤った入力、存在しないデータ、権限がない操作
- **境界値**: 最小・最大、その前後
- **組み合わせ**: 条件の組み合わせ（デシジョンテーブル）
- **状態**: 0 件、1 件、大量のデータ、二重送信

## 結果の記録と不具合

NG になったら、再現手順・期待結果・実際の結果・画面のコピーを残して、不具合として報告します。修正後は、同じテストと関連するテスト（回帰テスト）をもう一度実施します。

## ポイント

- テスト仕様書は、テストの前に作る
- 期待結果は、誰が見ても合否を判断できるよう具体的に書く
- 正常系だけでなく、異常系・境界値・状態の観点を洗い出す

> **確認しよう**
>
> - 「商品の数量を 1〜99 で入力する」欄のテストケースを、5 件以上書いてみましょう。
> - 期待結果「エラーが表示される」は、どう書き直すとよいでしょうか。
