## まずはここから

テスト仕様書は、『どう試して、何が起きれば正しいか』のメモです。別の人も同じ確認ができるように書きます。期待結果を『いい感じに動く』で済ませず、見て確かめられる形にしましょう。

### 最初に覚える4つの言葉

#### 前提条件

テストの前にそろえる状態。

**具体例：** ログイン済みであることを指定する。

#### 入力値

確認で使うデータ。

**具体例：** 数量に0を入れる。

#### 操作手順

確認するために行う操作の順番。

**具体例：** 入力してから登録ボタンを押す。

#### 期待結果

正しい場合に起きるべきこと。

**具体例：** エラー文が出て保存されないと決める。

### この講義の読み方

まず上の意味と具体例を確認し、下の4択に挑戦しましょう。詳しい仕組みやコードは「詳しい説明」、発展した内容は「Option」で後から読めます。1回で全てを暗記する必要はありません。

## テスト仕様書とは

「何を、どんな手順で、どんなデータでテストし、どうなれば合格か」をまとめた文書です。テストを始める **前に** 作ります。

- 誰が実施しても同じテストができる
- テストの漏れや重複に気づける
- 何をテストしたかの記録・証拠になる

## 書く項目

| 項目 | 内容 |
|---|---|
| テスト ID | 一意の番号（例: UT-LOGIN-001） |
| テスト対象 | 機能、画面、メソッド |
| テスト観点 | 何を確かめるか（正常系、異常系、境界値など） |
| 前提条件 | テスト前の状態（ログイン済み、データが 3 件ある など） |
| 手順 | 操作の順番 |
| 入力データ | 具体的な値 |
| 期待結果 | 合格となる結果。具体的に書く |
| 実施結果 | OK / NG、実施日、実施者 |
| 備考 | NG のときの不具合番号など |

## 例: ログイン機能

| ID | 観点 | 前提条件 | 入力 | 期待結果 |
|---|---|---|---|---|
| UT-LOGIN-001 | 正常系 | 社員番号 T001 が登録済み | T001 / 正しいパスワード | ホーム画面に移る |
| UT-LOGIN-002 | 異常系 | 同上 | T001 / 誤ったパスワード | 「社員番号またはパスワードが正しくありません」と表示し、ログイン画面のまま |
| UT-LOGIN-003 | 異常系 | — | 未登録の T999 / 任意 | UT-LOGIN-002 と同じメッセージ |
| UT-LOGIN-004 | 入力チェック | — | 社員番号を空欄 | 「社員番号を入力してください」と表示 |
| UT-LOGIN-005 | 境界値 | 同じ社員番号で 5 回失敗済み | T001 / 誤ったパスワード | 「試行回数が多すぎます」と表示 |

## 期待結果の書き方

あいまいな書き方では、合否を判断できません。

| あいまいな例 | 具体的な例 |
|---|---|
| 正しく表示される | 一覧に 3 件、登録日の新しい順に表示される |
| エラーになる | 「金額は 1 以上を入力してください」と赤字で表示され、保存されない |
| 速い | 3 秒以内に結果が表示される |

## 観点の洗い出し

- **正常系**: 想定どおりの入力・操作
- **異常系**: 誤った入力、存在しないデータ、権限がない操作
- **境界値**: 最小・最大、その前後
- **組み合わせ**: 条件の組み合わせ（デシジョンテーブル）
- **状態**: 0 件、1 件、大量のデータ、二重送信

## 結果の記録と不具合

NG になったら、再現手順・期待結果・実際の結果・画面のコピーを残して、不具合として報告します。修正後は、同じテストと関連するテスト（回帰テスト）をもう一度実施します。

## ポイント

- テスト仕様書は、テストの前に作る
- 期待結果は、誰が見ても合否を判断できるよう具体的に書く
- 正常系だけでなく、異常系・境界値・状態の観点を洗い出す

### 問1

「テストの前にそろえる状態」に当てはまるものはどれですか。

#### 選択肢

- A. 前提条件
- B. 入力値
- C. 期待結果
- D. 操作手順

#### 解答・解説

正解: A

**前提条件**：テストの前にそろえる状態。

例：ログイン済みであることを指定する。

### 問4

### 問5【応用】

期待結果として確認しやすいのは？

#### 選択肢

- A. 良い感じになる
- B. 何か表示されるかも
- C. たぶん大丈夫
- D. 数量エラーが出て保存されない

#### 解答・解説

正解: D

結果を具体的にすると、正しかったかを人によらず判断しやすくなります。

## Option：仕様とケースの対応を残す

要件とテストケースの対応が追えると、仕様変更時に更新すべきケースを見つけやすくなります。番号だけでなく、何のリスクを確かめるケースかも記録すると保守に役立ちます。

**やってみよう：** 注文数の上限が99から199へ変わった場合、どのケースと期待結果を変更するか洗い出してみましょう。
