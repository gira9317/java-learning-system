## まずはここから

同じ計算が正しく動くかを、毎回手で確かめるのは大変です。確認の手順もコードにして繰り返し使えます。Javaでそのテストを作るための道具の1つがJUnitです。

### 最初に覚える4つの言葉

#### JUnit

Java等の自動テストを作る道具。

**具体例：** 計算結果を繰り返し確認する。

#### 期待値

正しいはずの結果。

**具体例：** 2+3の正解を5と決める。

#### 実際の値

実行して得られた結果。

**具体例：** 作った計算メソッドの戻り値を見る。

#### assertEquals

期待値と実際の値を比較する検証。

**具体例：** 5になるはずの結果と実際を比べる。

### この講義の読み方

まず上の意味と具体例を確認し、下の4択に挑戦しましょう。詳しい仕組みやコードは「詳しい説明」、発展した内容は「Option」で後から読めます。1回で全てを暗記する必要はありません。

## JUnit とは

Java の **単体テストを自動化** するためのフレームワークです。テストをコードとして書いておくと、何度でも同じテストを一瞬で実行でき、変更で何かが壊れたらすぐに気づけます。現在は **JUnit 5**（JUnit Jupiter）が標準です。

## テストの書き方

テスト対象:

```java
public class Grader {
    public String grade(int score) {
        if (score < 0 || score > 100) {
            throw new IllegalArgumentException("0〜100 で指定してください");
        }
        return score >= 60 ? "合格" : "不合格";
    }
}
```

テストコード（通常 `src/test/java` に置く）:

```java
import static org.junit.jupiter.api.Assertions.*;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;

class GraderTest {

    private final Grader grader = new Grader();

    @Test
    void 六十点は合格() {
        assertEquals("合格", grader.grade(60));
    }

    @Test
    void 五十九点は不合格() {
        assertEquals("不合格", grader.grade(59));
    }

    @Test
    void 範囲外は例外() {
        assertThrows(IllegalArgumentException.class, () -> grader.grade(101));
    }

    @ParameterizedTest
    @CsvSource({ "0, 不合格", "100, 合格", "80, 合格" })
    void 境界と代表値(int score, String expected) {
        assertEquals(expected, grader.grade(score));
    }
}
```

## よく使うアノテーションとメソッド

| 名前 | 内容 |
|---|---|
| `@Test` | テストメソッドの印 |
| `@ParameterizedTest` | 引数を変えて同じテストを繰り返す |
| `@BeforeEach` / `@AfterEach` | 各テストの前・後に実行する（準備・後片付け） |
| `@DisplayName` | テスト結果に表示する名前 |
| `assertEquals(期待値, 実際の値)` | 等しいか |
| `assertTrue` / `assertFalse` | 真か / 偽か |
| `assertNull` / `assertNotNull` | null か / null でないか |
| `assertThrows` | 例外が投げられるか |

`assertEquals` は **期待値を先に** 書きます。逆にすると、失敗時のメッセージが紛らわしくなります。

## テストの組み立て方（AAA）

1 つのテストを、3 つの部分に分けて書くと読みやすくなります。

```java
@Test
void 会員は一割引() {
    // Arrange（準備）
    Cart cart = new Cart(new MemberDiscount());
    // Act（実行）
    int total = cart.total(1000);
    // Assert（確認）
    assertEquals(900, total);
}
```

## 良いテストの条件

- **1 つのテストで 1 つのこと** を確かめる
- **独立している**: 実行順や、ほかのテストの結果に左右されない
- **何度実行しても同じ結果**: 現在時刻や乱数、外部の DB に依存しない（必要なら差し替える）
- **速い**: すぐ実行できるから、頻繁に実行できる
- **名前で内容がわかる**: 何を確かめるテストか、名前だけで伝わる

## 実行方法

- IDE: テストクラスやメソッドの横の実行ボタン
- Maven: `mvn test`
- Gradle: `gradle test`

CI（自動ビルド）でもテストを実行し、失敗したらマージしないようにします。

## ポイント

- JUnit で単体テストをコードにして、何度でも自動で実行する
- `assertEquals(期待値, 実際の値)` が基本
- 境界値は `@ParameterizedTest` でまとめて書ける
- テストは独立・再現可能・速く、1 つのことを確かめる

## Option：値だけでなく振る舞いの契約を確かめる

内部の細かい呼び出し回数だけを固定すると、同じ結果を返す改善でもテストが壊れます。利用者が必要とする結果や副作用を中心に検証し、外部通信等の重要な契約に必要な範囲でモックを使います。

**やってみよう：** 同じ計算をループからStreamへ変えても有効なテストを考えてみましょう。
