## 機能分割とは

大きな機能を、**小さく、役割がはっきりした部品** に分けることです。部品に分けると、1 つずつ作ってテストでき、複数人で分担でき、修正の影響も小さくできます。

## 分け方の考え方

大きな機能から、段階的に細かくしていきます（**段階的詳細化**、トップダウン）。

```text
社員の給与計算
├─ 勤怠データを読み込む
│   ├─ CSV ファイルを開く
│   └─ 1 行ずつ勤怠データに変換する
├─ 給与を計算する
│   ├─ 基本給を求める
│   ├─ 残業代を求める
│   └─ 控除額を求める
└─ 給与明細を出力する
```

それぞれの部品が「1 つのことだけをする」まで分けます。

## 良い分割の目安

| 目安 | 内容 |
|---|---|
| 凝集度は高く | 1 つの部品の中身が、1 つの目的にまとまっている |
| 結合度は低く | 部品どうしの依存が少なく、受け渡すデータが必要最小限 |
| 名前で説明できる | 「〇〇を△△する」と短く言える。「〇〇と××もする」になったら分ける |
| 大きすぎない | メソッドなら画面に収まる長さが目安 |

## コードで見る

分割する前:

```java
void process(String file) {
    // ファイルを読む処理が 30 行
    // 計算する処理が 40 行
    // 出力する処理が 30 行
}
```

分割したあと:

```java
void process(Path file) {
    List<Attendance> records = readAttendance(file);
    List<Payslip> payslips = calculate(records);
    printPayslips(payslips);
}
```

`process` を読むだけで全体の流れがわかり、`calculate` だけをテストすることもできます。

## 層（レイヤー）で分ける

業務システムでは、役割ごとに層を分けるのが一般的です。

| 層 | 役割 | 例 |
|---|---|---|
| プレゼンテーション層 | 画面・API の入口。入力を受け、結果を返す | Controller、サーブレット |
| ビジネスロジック層 | 業務のルールに沿って処理する | Service |
| データアクセス層 | DB やファイルの読み書き | Repository、DAO |

画面の変更が計算処理に、DB の変更が画面に影響しにくくなります。

## ポイント

- 大きな機能は、段階的に小さく分ける
- 1 つの部品には 1 つの役割。名前で説明できる大きさにする
- 部品の中はまとまり（凝集度が高い）、部品の間はゆるく（結合度が低い）

> **確認しよう**
>
> - 「会員登録」の機能を、3〜5 個の部品に分けてみましょう。
> - 「入力チェックして、DB に保存して、メールも送る」メソッドを分けるとしたら、どう分けますか。
