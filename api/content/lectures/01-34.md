## まずはここから

大きな仕事は、小さな役割へ分けると考えやすくなります。料理でも、下ごしらえ・調理・盛り付けを分けます。プログラムも『入力を確かめる』『保存する』などの役割を分けて作ります。

### 最初に覚える4つの言葉

#### 機能分割

仕事を小さな役割へ分けること。

**具体例：** 登録を入力確認と保存へ分ける。

#### 入力チェック

受け取った値が使えるか確認すること。

**具体例：** 名前が空でないか調べる。

#### 保存処理

データを後でも使えるよう残すこと。

**具体例：** 登録内容をDBへ書く。

#### 責務

その部品が担当する役割。

**具体例：** メールを送る部品は通知を担当する。

### この講義の読み方

まず上の意味と具体例を確認し、下の4択に挑戦しましょう。詳しい仕組みやコードは「詳しい説明」、発展した内容は「Option」で後から読めます。1回で全てを暗記する必要はありません。

## 機能分割とは

大きな機能を、**小さく、役割がはっきりした部品** に分けることです。部品に分けると、1 つずつ作ってテストでき、複数人で分担でき、修正の影響も小さくできます。

## 分け方の考え方

大きな機能から、段階的に細かくしていきます（**段階的詳細化**、トップダウン）。

```text
社員の給与計算
├─ 勤怠データを読み込む
│   ├─ CSV ファイルを開く
│   └─ 1 行ずつ勤怠データに変換する
├─ 給与を計算する
│   ├─ 基本給を求める
│   ├─ 残業代を求める
│   └─ 控除額を求める
└─ 給与明細を出力する
```

それぞれの部品が「1 つのことだけをする」まで分けます。

## 良い分割の目安

| 目安 | 内容 |
|---|---|
| 凝集度は高く | 1 つの部品の中身が、1 つの目的にまとまっている |
| 結合度は低く | 部品どうしの依存が少なく、受け渡すデータが必要最小限 |
| 名前で説明できる | 「〇〇を△△する」と短く言える。「〇〇と××もする」になったら分ける |
| 大きすぎない | メソッドなら画面に収まる長さが目安 |

## コードで見る

分割する前:

```java
void process(String file) {
    // ファイルを読む処理が 30 行
    // 計算する処理が 40 行
    // 出力する処理が 30 行
}
```

分割したあと:

```java
void process(Path file) {
    List<Attendance> records = readAttendance(file);
    List<Payslip> payslips = calculate(records);
    printPayslips(payslips);
}
```

`process` を読むだけで全体の流れがわかり、`calculate` だけをテストすることもできます。

## 層（レイヤー）で分ける

業務システムでは、役割ごとに層を分けるのが一般的です。

| 層 | 役割 | 例 |
|---|---|---|
| プレゼンテーション層 | 画面・API の入口。入力を受け、結果を返す | Controller、サーブレット |
| ビジネスロジック層 | 業務のルールに沿って処理する | Service |
| データアクセス層 | DB やファイルの読み書き | Repository、DAO |

画面の変更が計算処理に、DB の変更が画面に影響しにくくなります。

## ポイント

- 大きな機能は、段階的に小さく分ける
- 1 つの部品には 1 つの役割。名前で説明できる大きさにする
- 部品の中はまとまり（凝集度が高い）、部品の間はゆるく（結合度が低い）

### 問5【応用】

1つの処理が入力確認も保存も通知も全て持つ場合、改善の候補は？

#### 選択肢

- A. 名前を消す
- B. 必ず全て1行へ詰める
- C. エラーを無視する
- D. 役割ごとに整理する

#### 解答・解説

正解: D

分けることで、何を担当する処理か分かりやすくなります。分けた後の連携も必要です。

## Option：境界を越える失敗に備える

DBと外部サービスへの操作は、まとめて完全成功・完全失敗にしにくいことがあります。保存した通知要求を後で確実に送るOutboxなど、失敗しても再試行できる構成が選択肢になります。

**やってみよう：** 『保存成功・通知失敗』を利用者と管理者にどう見せるか、状態遷移を書いてみましょう。
