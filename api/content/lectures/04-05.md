## NoSQL とは

「**Not only SQL**」の略として使われ、RDB（表と SQL）以外の方式のデータベースをまとめた呼び方です。表の形に当てはめにくいデータや、非常に大量のデータ・アクセスを扱うために発展しました。

## 主な種類

| 種類 | データの持ち方 | 代表例 | 向いている用途 |
|---|---|---|---|
| キーバリュー型 | キーと値の組 | Redis、Amazon DynamoDB | セッション、キャッシュ、ランキング |
| ドキュメント型 | JSON のような文書 | MongoDB、Firestore | 項目が自由に変わるデータ、商品カタログ |
| カラム指向型（ワイドカラム型） | 行ごとに違う列を持てる | Apache Cassandra | 大量のログ、時系列データ |
| グラフ型 | ノードとその関係 | Neo4j | SNS のつながり、おすすめ |

### キーバリュー型の例

```text
SET session:abc123 "user:42"   （値を保存）
GET session:abc123             （キーで取り出す）→ "user:42"
EXPIRE session:abc123 3600     （1 時間で自動的に消す）
```

メモリ上で動くものが多く、非常に高速です。

### ドキュメント型の例

```json
{
  "_id": "p-1001",
  "name": "ノート PC",
  "price": 98000,
  "specs": { "cpu": "8 コア", "memory": "16GB" },
  "tags": ["PC", "仕事用"]
}
```

1 件ごとに項目が違ってもよく、関連するデータを 1 つの文書にまとめて持てます。

## RDB との比較

| | RDB | NoSQL（一般的な傾向） |
|---|---|---|
| データの構造 | 表。事前にスキーマを決める | 製品ごとに違う。スキーマが柔軟 |
| 問い合わせ | SQL で複雑な結合・集計ができる | 結合は苦手なものが多い。キーでの取り出しが速い |
| 一貫性 | トランザクション（ACID）で強く守る | 速さや規模のために、一時的な不一致を許すものもある（結果整合性） |
| 規模の拡大 | 主に 1 台を強化する（スケールアップ） | 台数を増やして分散しやすい（スケールアウト） |

## 使い分け

- **業務データの中心**（受注、会計、社員など、整合性が大切なもの）は RDB
- **セッション・キャッシュ・一時的なデータ** は Redis などのキーバリュー型
- **項目が頻繁に変わる、構造がまちまちのデータ** はドキュメント型
- 1 つのシステムで、RDB と NoSQL を **組み合わせる** ことも多い

最近の RDB は JSON 型の列（PostgreSQL の `jsonb` など）にも対応しており、「柔軟な項目は JSON 列に入れる」という方法もあります。

## ポイント

- NoSQL は RDB 以外のデータベースの総称。キーバリュー・ドキュメント・カラム指向・グラフなど
- 速さ・柔軟さ・分散のしやすさと引き換えに、結合や強い一貫性が苦手なものが多い
- 用途に応じて RDB と組み合わせて使う

> **確認しよう**
>
> - ログイン中のユーザーのセッション情報を保存するのに、キーバリュー型が向いているのはなぜでしょうか。
> - 銀行の口座残高を、一時的な不一致を許す仕組みで管理すると、どんな問題が起きるでしょうか。
