## まずはここから

ページを移ってもログインが続くのは、利用者を関連付ける仕組みがあるからです。Cookieはブラウザが保存して送る小さな情報、セッションはそれを手掛かりに状態を関連付ける仕組みです。

### 最初に覚える4つの言葉

#### Cookie

ブラウザが条件に応じて保存・送信する情報。

**具体例：** サーバーとのやり取りで識別情報を送る。

#### セッション

継続した利用状態を関連付ける仕組み。

**具体例：** どの利用者の操作かを確認する。

#### ログアウト

ログイン状態を終了する操作。

**具体例：** 使い終えて認証状態を終える。

#### 有効期限

利用できる期間の終わり。

**具体例：** 一定時間でセッションを使えなくする。

### この講義の読み方

まず上の意味と具体例を確認し、下の4択に挑戦しましょう。詳しい仕組みやコードは「詳しい説明」、発展した内容は「Option」で後から読めます。1回で全てを暗記する必要はありません。

## なぜ必要か

HTTP は **ステートレス** で、サーバーは前のリクエストを覚えていません。そのままでは「ログインした人」と「次の画面を開いた人」が同じ人かわかりません。複数のリクエストをまたいで状態を保つための仕組みが、**Cookie** と **セッション** です。

## Cookie

サーバーがブラウザに保存させる、小さなデータです。

1. サーバーがレスポンスで `Set-Cookie` を送る
2. ブラウザは Cookie を保存し、以降 **同じサイトへのリクエストに自動で付けて** 送る

```http
HTTP/1.1 200 OK
Set-Cookie: session=Hl5IZXRvb2s; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=86400
```

```http
GET /home HTTP/1.1
Cookie: session=Hl5IZXRvb2s
```

## Cookie の属性

| 属性 | 意味 |
|---|---|
| `Expires` / `Max-Age` | 有効期限。指定しないと、ブラウザを閉じると消える |
| `Path` / `Domain` | どの URL に送るか |
| `HttpOnly` | JavaScript から読めなくする。盗まれにくくなる |
| `Secure` | HTTPS のときだけ送る |
| `SameSite` | ほかのサイトから来たリクエストに付けるかどうか（`Strict` / `Lax` / `None`） |

**セッション ID を入れる Cookie には、`HttpOnly`・`Secure`・`SameSite` を付けます**。

## セッション

利用者ごとの状態（ログインしているユーザー、入力途中のデータなど）を、**サーバー側** に保存する仕組みです。ブラウザには、その状態を見つけるための **セッション ID** だけを Cookie で渡します。

```text
ブラウザ                       サーバー
 │── ログイン（ID とパスワード）─→│ 本人確認 → セッションを作る
 │←─ Set-Cookie: session=XYZ ──│ （XYZ → ユーザー 42 を保存）
 │── GET /home  Cookie: XYZ ──→│ XYZ を探す → ユーザー 42 とわかる
```

| | Cookie だけで状態を持つ | セッション |
|---|---|---|
| 状態の置き場所 | ブラウザ | サーバー |
| 書き換えの危険 | 利用者が自由に書き換えられる | ブラウザには ID しかない |
| 向いているもの | 表示設定など、改ざんされても困らないもの | ログイン状態、権限、個人情報 |

**ログイン中のユーザー ID や権限を、Cookie にそのまま入れてはいけません**。書き換えられて、ほかの人になりすまされます。

## Java（サーブレット）でのセッション

```java
// ログイン成功時
HttpSession old = req.getSession(false);
if (old != null) old.invalidate();         // 古いセッションは捨てる
HttpSession session = req.getSession(true); // 新しいセッション ID を発行
session.setAttribute("userId", user.getId());

// ほかの画面で
Long userId = (Long) req.getSession().getAttribute("userId");

// ログアウト時
req.getSession().invalidate();
```

## セッションの安全

| 攻撃 | 内容 | 対策 |
|---|---|---|
| セッションハイジャック | セッション ID を盗まれ、なりすまされる | HTTPS、`HttpOnly`・`Secure`、推測できない ID |
| セッション固定 | 攻撃者が用意した ID を使わせ、ログイン後に乗っ取る | ログインしたら新しいセッション ID を発行する |
| CSRF | ほかのサイトから、ログイン中の利用者に意図しないリクエストを送らせる | `SameSite`、送信元（Origin）の確認、CSRF トークン |

このシステムも、ランダムなトークンを `HttpOnly` の Cookie に入れ、サーバー側の DB でユーザーを特定するセッション方式です。

## ポイント

- HTTP はステートレス。状態を保つために Cookie とセッションを使う
- ブラウザにはセッション ID だけ、大事な情報はサーバー側に置く
- セッション ID の Cookie には `HttpOnly`・`Secure`・`SameSite`
- ログインのたびに新しいセッション ID を発行する

## Option：サイトとオリジンの違い

オリジンはスキーム・ホスト・ポートの組で、CookieのSameSiteが使うサイトの概念とは異なります。サブドメインやポートを変えた開発構成では、CORSとCookieの条件を別々に確認しましょう。

**参考：** [MDN：Cookieの利用](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)。

**やってみよう：** localhostの3000番と4000番が、オリジンとして同じか違うか説明してみましょう。
