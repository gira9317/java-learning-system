## なぜ読みやすさが大切か

コードは、書かれる回数より **読まれる回数のほうがずっと多い** ものです。不具合の調査、機能の追加、引き継ぎのたびに、自分やほかの人が読みます。読みやすいコードは、間違いに気づきやすく、直しやすくなります。

## Java の命名規則

| 対象 | 書き方 | 例 |
|---|---|---|
| クラス・インターフェース | パスカルケース（単語の先頭を大文字） | `EmployeeService`、`Shape` |
| メソッド・変数 | キャメルケース（2 語目から先頭を大文字） | `calculateTotal`、`userName` |
| 定数（static final） | 大文字のスネークケース | `MAX_RETRY_COUNT` |
| パッケージ | すべて小文字。ドメインを逆にする | `com.example.payroll` |

## 良い名前の付け方

| 悪い例 | 良い例 | 理由 |
|---|---|---|
| `d` | `elapsedDays` | 何の値かわかる |
| `list` | `activeMembers` | 中身がわかる |
| `flag` | `isPaid` / `hasError` | 真偽値は is / has / can で始めると意味がわかる |
| `doIt()` | `sendInvoiceMail()` | 何をするかがわかる |
| `getData2()` | `findByDepartment()` | 番号ではなく違いを名前にする |
| `tmp` | `previousTotal` | 一時的でも役割を名前にする |

- メソッドは **動詞** で始める（`get`、`find`、`create`、`update`、`calculate`、`is`）
- クラスは **名詞**
- 省略しすぎない（`cnt` より `count`）。ただし、`i`（ループ変数）や `id` のように広く通じるものはよい

## マジックナンバーを避ける

意味のわからない数値を直接書かず、名前を付けた定数にします。

```java
// 悪い例
if (age >= 20 && total > 5000) { ... }

// 良い例
static final int ADULT_AGE = 20;
static final int FREE_SHIPPING_THRESHOLD = 5000;

if (age >= ADULT_AGE && total > FREE_SHIPPING_THRESHOLD) { ... }
```

## 読みやすい書き方

- **1 つのメソッドは 1 つの仕事**。長くなったら分ける
- **ネストを浅く**。条件に合わないときは早めに `return` する（ガード節）
- **インデントとスペースをそろえる**。IDE の自動整形を使う
- **似た処理をコピーしない**。共通のメソッドにまとめる

## コメントの書き方

コメントには「**何をしているか**」より「**なぜそうしているか**」を書きます。何をしているかは、コードと名前で伝えます。

```java
// 悪い例（コードを読めばわかる）
// i を 1 増やす
i++;

// 良い例（理由はコードからわからない）
// 取引先のシステムが 1 秒に 10 件までしか受け付けないため、間隔を空ける
Thread.sleep(100);
```

- 使わなくなったコードは、コメントアウトで残さず削除する（履歴は Git に残る）
- 公開するメソッドには Javadoc（`/** ... */`）で、役割・引数・戻り値・例外を書く

## コーディング規約

チームやプロジェクトで決めた書き方のルールです。Google Java Style Guide などの公開された規約をもとにすることが多く、Checkstyle などのツールで自動チェックできます。**プロジェクトの規約が最優先** です。

## ポイント

- 名前で「何か」「何をするか」が伝わるようにする
- Java はクラスがパスカルケース、メソッド・変数がキャメルケース、定数が大文字
- マジックナンバーは定数に。コメントには理由を書く

> **確認しよう**
>
> - `int x = p * 108 / 100;` を、読みやすく書き直してみましょう。
> - 自分が書いたコードの変数名を見直して、名前だけで役割が伝わるか確かめてみましょう。
