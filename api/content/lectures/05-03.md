## 認証と認可

| 用語 | 内容 | 例 |
|---|---|---|
| 認証（Authentication） | **本人であること** を確かめる | 社員番号とパスワードでログインする |
| 認可（Authorization） | 認証した相手に、**何を許可するか** を決める | 研修担当者だけが提出をレビューできる |

認証が「入館証の確認」なら、認可は「どの部屋に入ってよいか」です。

## 認証の 3 つの要素

| 要素 | 内容 | 例 |
|---|---|---|
| 知識情報 | 本人だけが知っていること | パスワード、暗証番号 |
| 所持情報 | 本人だけが持っているもの | スマートフォン（認証アプリ、SMS）、IC カード、セキュリティキー |
| 生体情報 | 本人の身体の特徴 | 指紋、顔 |

2 つ以上の **違う種類** の要素を組み合わせることを **多要素認証（MFA）** といいます。パスワードが漏れても、スマートフォンがなければログインできないため、安全性が大きく上がります。（パスワードと秘密の質問は、どちらも知識情報なので多要素ではありません。）

## パスワード認証を安全に作る

### 保存

- パスワードは **平文でも、元に戻せる暗号化でもなく、ハッシュ化** して保存する
- ソルト付きで、計算を重くした専用の方式（**Argon2**、bcrypt、PBKDF2）を使う

### ログイン

- 失敗したときのメッセージは「**ID またはパスワードが正しくありません**」とし、どちらが違うかを教えない（登録されている ID を探られないため）
- **試行回数を制限** する（次の講義「ブルートフォース攻撃」）
- 通信は HTTPS で

### セッション

- ログインしたら、**新しいセッション ID** を発行する
- ログアウトしたら、サーバー側のセッションを消す
- パスワードを変えたら、ほかの端末のセッションも無効にする

## このシステムの認証

この学習システムも、次の考え方で作られています。

- パスワードは Argon2 でハッシュ化して保存
- ログインの失敗は、社員番号ごと・接続元ごとに回数を制限
- ログインするとランダムなトークンを発行し、`HttpOnly` の Cookie に入れる。DB にはトークンのハッシュだけを保存
- 初期パスワードのままでは使えず、最初に変更を求める
- 研修担当者の機能は、サーバー側で役割（role）を確認してから実行する（認可）

## トークンと外部の認証

| 方式 | 内容 |
|---|---|
| セッション（Cookie） | サーバーがログイン状態を保存し、ブラウザには ID だけを渡す。Web アプリケーションで一般的 |
| トークン（JWT など） | 署名付きのトークンに情報を入れて渡す。スマホアプリや API で使われる |
| シングルサインオン（SSO） | 一度のログインで、複数のシステムを使える。会社のアカウント（Microsoft、Google など）でログインする |
| OAuth 2.0 / OpenID Connect | ほかのサービスの認証を利用したり、権限を委ねたりするための標準 |

## 認可は必ずサーバーで

画面でボタンを隠しても、API を直接呼ばれれば実行されてしまいます。

- **API ごとに、サーバー側で権限を確認** する
- 「自分のデータか」も確認する（URL の ID を書き換えて、他人のデータを見られないように）
- ユーザー ID や権限を、クライアントから送られた値で判断しない

## ポイント

- 認証は本人確認、認可は許可の判断
- 多要素認証は、違う種類の要素を組み合わせる
- パスワードはソルト付きの専用方式でハッシュ化し、試行回数を制限する
- 認可はすべてサーバー側で確認する

> **確認しよう**
>
> - 「パスワード + 秘密の質問」が多要素認証にならない理由を説明してみましょう。
> - `GET /api/orders/123` で、他人の注文が見えないようにするには、サーバーで何を確認すればよいでしょうか。
