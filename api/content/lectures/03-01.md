## まずはここから

ページを開くと、ブラウザはサーバーへ『これをください』と頼み、サーバーが返答します。このやり取りの約束の1つがHTTPです。まずはお願いと返答の1往復をイメージしましょう。

### 最初に覚える4つの言葉

#### リクエスト

サーバー等へ送る要求。

**具体例：** 講義ページをくださいと頼む。

#### レスポンス

要求に対する応答。

**具体例：** ページや結果を返す。

#### ステータスコード

応答の状態を表す番号。

**具体例：** 404で対象が見つからないことを示す。

#### ヘッダー

通信へ付ける補足情報。

**具体例：** 本文がJSONであることを伝える。

### この講義の読み方

まず上の意味と具体例を確認し、下の4択に挑戦しましょう。詳しい仕組みやコードは「詳しい説明」、発展した内容は「Option」で後から読めます。1回で全てを暗記する必要はありません。

## HTTP とは

**HyperText Transfer Protocol** の略で、Web ブラウザと Web サーバーがやりとりするための決まりです。クライアント（ブラウザやアプリ）が **リクエスト** を送り、サーバーが **レスポンス** を返します。

- 通常は TCP のポート 80（HTTPS は 443）を使う
- **ステートレス**: サーバーは、前のリクエストの内容を覚えていない（覚えておくための仕組みがセッションと Cookie）
- テキストで書かれていて、人が読める（HTTP/1.1 の場合）

## URL の構造

```text
https://www.example.com:443/members/search?dept=dev&page=2#result
```

| 部分 | 例 | 内容 |
|---|---|---|
| スキーム | `https` | 使うプロトコル |
| ホスト | `www.example.com` | 接続先のサーバー |
| ポート | `443` | 省略すると http は 80、https は 443 |
| パス | `/members/search` | サーバーの中のどのリソースか |
| クエリ文字列 | `dept=dev&page=2` | `?` のあとの `名前=値` の並び |
| フラグメント | `result` | ページ内の位置。サーバーには送られない |

## リクエスト

```http
POST /members HTTP/1.1
Host: www.example.com
Content-Type: application/json
Cookie: session=abc123

{"name": "山田", "dept": "dev"}
```

| 部分 | 内容 |
|---|---|
| リクエスト行 | メソッド・パス・バージョン |
| ヘッダー | 付加情報（宛先のホスト、データの形式、Cookie など） |
| 空行 | ヘッダーの終わり |
| ボディ | 送るデータ（POST などで使う） |

## レスポンス

```http
HTTP/1.1 201 Created
Content-Type: application/json
Set-Cookie: session=abc123; HttpOnly; Secure

{"id": 42, "name": "山田"}
```

## 主なメソッド

| メソッド | 用途 |
|---|---|
| GET | 取得する |
| POST | 新しく作る、処理を依頼する |
| PUT | 置き換える |
| PATCH | 一部を変更する |
| DELETE | 削除する |

## ステータスコード

| 範囲 | 意味 | 代表例 |
|---|---|---|
| 1xx | 処理中 | 101 Switching Protocols |
| 2xx | 成功 | 200 OK、201 Created、204 No Content |
| 3xx | リダイレクト | 301 Moved Permanently、302 Found、304 Not Modified |
| 4xx | クライアント側の誤り | 400 Bad Request、401 Unauthorized、403 Forbidden、404 Not Found、409 Conflict、429 Too Many Requests |
| 5xx | サーバー側の誤り | 500 Internal Server Error、502 Bad Gateway、503 Service Unavailable |

不具合を調べるときは、まずステータスコードを見て「送った側の問題か、サーバー側の問題か」を切り分けます。

## よく使うヘッダー

| ヘッダー | 内容 |
|---|---|
| `Host` | 接続先のホスト名 |
| `Content-Type` | ボディの形式（`text/html`、`application/json` など） |
| `Content-Length` | ボディの長さ |
| `Cookie` / `Set-Cookie` | Cookie の送信 / 保存の指示 |
| `Authorization` | 認証情報（トークンなど） |
| `Location` | リダイレクト先 |
| `Cache-Control` | キャッシュの扱い |

## HTTPS

HTTP の通信を **TLS** で暗号化したものです。盗み見・改ざん・なりすましを防ぎます。現在の Web サイトは HTTPS が基本で、ログインや個人情報を扱う画面では必須です（第 5 章「セキュアレイヤー」）。

## バージョン

- **HTTP/1.1**: テキスト形式。広く使われてきた
- **HTTP/2**: 1 つの接続で複数のリクエストを並行して送り、速くした
- **HTTP/3**: UDP をもとにした QUIC を使い、さらに速くした

アプリケーションから見たメソッドやステータスコードの意味は同じです。

## ポイント

- HTTP はリクエストとレスポンスのやりとり。ステートレス
- メソッドで「何をしたいか」、ステータスコードで「どうなったか」を表す
- 4xx はクライアント、5xx はサーバーの問題
- 実際の運用では HTTPS を使う

### 問5【応用】

404という応答が来た時の基本的な意味は？

## Option：待ち時間を分けて測る

名前解決、接続、TLS、サーバー処理、本文転送、画面描画では原因と対策が違います。『ページが遅い』を1つの数値だけで捉えず、どの段階の時間かをそろえて比較します。

**やってみよう：** 開発者ツールのNetworkで、初回アクセスと2回目を比べ、接続・待機・転送の時間を確認してみましょう。
