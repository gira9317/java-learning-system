## まずはここから

DBへのお願いであるSQLへ、利用者の文字をそのままつなぐと、その文字が命令として解釈される場合があります。これがSQLインジェクションの入口です。命令と入力データを分けることが基本です。

### 最初に覚える4つの言葉

#### SQL

DBへ検索や更新等を頼む言葉。

**具体例：** 社員の情報を検索する。

#### SQLインジェクション

入力によりSQLの命令の意味が変わる攻撃。

**具体例：** 検索語が命令の一部になってしまう。

#### プレースホルダー

SQLの値を別に渡すための枠。

**具体例：** 検索する名前を命令と分けて渡す。

#### 入力チェック

受け取った値の型や範囲等を確認すること。

**具体例：** IDが正の整数か確かめる。

まず上の意味と具体例を確認し、下の4択に挑戦しましょう。詳しい仕組みやコードは「詳しい説明」、発展した内容は「Option」で後から読めます。1回で全てを暗記する必要はありません。

## どんな攻撃か

入力欄などから **SQL の一部を注入** して、アプリケーションが意図していない SQL を実行させる攻撃です。データの盗み出し、改ざん、削除、ログインの突破などにつながる、非常に危険な脆弱性です。

利用者の入力を、**文字列の連結で SQL に埋め込む** と起きます。

```java
// 危険な例
String sql = "SELECT * FROM users WHERE employee_no = '" + employeeNo
           + "' AND password = '" + password + "'";
```

## 攻撃の例

### ログインの突破

社員番号の欄に次を入力すると:

```text
' OR '1'='1' --
```

組み立てられる SQL は:

```sql
SELECT * FROM users WHERE employee_no = '' OR '1'='1' --' AND password = '...'
```

- `'1'='1'` は常に真なので、すべての行に当てはまる
- `--` 以降はコメントになり、パスワードの条件が無視される

その結果、パスワードを知らなくてもログインできてしまいます。

### データの盗み出し・破壊

```text
' UNION SELECT employee_no, password_hash FROM users --
'; DROP TABLE users; --
```

ほかの表の中身を表示させたり、表を削除したりできてしまうことがあります。

## 対策: プレースホルダーを使う

SQL の **形** と **値** を分けて送る方法です。値はどんな文字が含まれていても「値」として扱われ、SQL の一部として解釈されません。

```java
String sql = "SELECT * FROM users WHERE employee_no = ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, employeeNo);
    try (ResultSet rs = ps.executeQuery()) {
        ...
    }
}
```

このシステムの API も、すべての SQL で `$1`、`$2` のプレースホルダーを使っています。

```javascript
await pool.query(
  `SELECT id, password_hash FROM users WHERE employee_no = $1`,
  [employeeNo],
);
```

## プレースホルダーが使えない部分

テーブル名、列名、`ORDER BY` の並び順などは、プレースホルダーで渡せません。利用者の入力で切り替えたいときは、**決められた候補の中から選ぶ**（ホワイトリスト）ようにします。

```java
String column = switch (sortParam) {
    case "name" -> "name";
    case "hired" -> "hired_on";
    default -> "id";
};
String sql = "SELECT * FROM employees ORDER BY " + column;
```

## 被害を小さくする

- アプリケーションが使う DB ユーザーの **権限を最小限に** する（`DROP` などの権限を与えない）
- エラー画面に、SQL や DB のエラーの詳細を表示しない（攻撃の手がかりになる）
- パスワードはハッシュ化して保存しておく（盗まれても、すぐには使えない）

## ORM やフレームワークでも油断しない

JPA や MyBatis などの多くの仕組みは、普通に使えばプレースホルダーになります。しかし、文字列を連結して SQL や JPQL を組み立てる書き方（MyBatis の `${}` など）をすると、同じ脆弱性が生まれます。

## ポイント

- SQL に入力を文字列連結で埋め込まない
- 必ずプレースホルダー（`PreparedStatement`）を使う
- 列名や並び順は、ホワイトリストから選ぶ
- DB ユーザーの権限を最小限にする

## Option：入力検証とパラメーター化は役割が違う

商品IDが正の整数かを検証することと、SQLの命令と値を分離することは両方必要です。文字を削るだけの独自対策に頼らず、DBドライバーのパラメーター化を使います。

**参考：** [OWASP：SQLインジェクション対策](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet)。

**やってみよう：** 値はパラメーター化し、並び順は許可リストで選ぶ検索APIを設計してみましょう。
