## まずはここから

システム作りは、コードを書くことだけではありません。何を作るか相談し、作り方を決め、動きを確かめる段階があります。家を建てるときも、希望を聞く・設計する・建てる・検査する順番があります。

### 最初に覚える4つの言葉

#### 要件定義

何を実現するかを決めること。

**具体例：** 誰がどんな作業をしたいか相談する。

#### 設計

実現の仕方を決めること。

**具体例：** 画面やデータのつながりを考える。

#### 実装

決めた動きをコード等で作ること。

**具体例：** 画面や計算処理を書く。

#### テスト

期待した動作かを確かめること。

**具体例：** ボタンを押した結果を確認する。

### この講義の読み方

まず上の意味と具体例を確認し、下の4択に挑戦しましょう。詳しい仕組みやコードは「詳しい説明」、発展した内容は「Option」で後から読めます。1回で全てを暗記する必要はありません。

## 開発工程とは

システムを作るときの作業を、順番に分けたものです。一般的には次の工程があります。

| 工程 | 内容 | 主な成果物 |
|---|---|---|
| 要件定義 | 何を作るか、何ができればよいかを決める | 要件定義書 |
| 基本設計（外部設計） | 利用者から見た仕様（画面、帳票、機能）を決める | 基本設計書、画面設計書 |
| 詳細設計（内部設計） | プログラムの作り（クラス、処理、DB）を決める | 詳細設計書 |
| 実装（製造） | プログラムを書く | ソースコード |
| 単体テスト | 部品ごとに正しく動くか確かめる | テスト仕様書・結果 |
| 結合テスト | 部品を組み合わせて確かめる | 同上 |
| 総合テスト（システムテスト） | システム全体が要件を満たすか確かめる | 同上 |
| 受け入れテスト | 利用者が確かめる | 同上 |
| 運用・保守 | 動かし続け、不具合の修正や改善をする | 運用手順書 |

## V 字モデル

設計の工程と、テストの工程が対応していることを表した図です。

```text
要件定義 ─────────────────── 受け入れテスト
  基本設計 ───────────── 総合テスト
    詳細設計 ─────── 結合テスト
      実装 ── 単体テスト
```

上の工程で決めたことを、対応するテストで確かめます。例えば、詳細設計で決めたクラス間の連携は、結合テストで確認します。

## 主な開発手法

### ウォーターフォール

上の工程から順番に進め、原則として前の工程に戻らない手法です。

- 長所: 計画や進み具合を管理しやすい。大規模で要件が固まっている開発に向く
- 短所: 途中の要件変更に弱い。動くものが見えるのが遅い

### アジャイル

短い期間（1〜4 週間）で「計画 → 作る → 確かめる」を繰り返し、少しずつ機能を増やす手法の総称です。代表的なものに **スクラム** があります。

- 長所: 変化に強い。早い段階から動くものを見せて意見をもらえる
- 短所: 全体の期間や費用を最初に決めにくい

| スクラムの用語 | 内容 |
|---|---|
| スプリント | 1〜4 週間の開発の区切り |
| プロダクトバックログ | 作りたいものの一覧（優先順位付き） |
| デイリースクラム | 毎日 15 分程度の短い打ち合わせ |
| スプリントレビュー | できたものを関係者に見せる |
| レトロスペクティブ | 進め方を振り返って改善する |

### そのほか

- **プロトタイピング**: 試作品を作って、利用者に確かめてもらいながら要件を固める
- **スパイラルモデル**: 設計から実装までを繰り返し、少しずつ完成度を上げる

## 新人が意識すること

- 自分の作業が、どの工程の何にあたるかを把握する
- 設計書と違う作りにするときは、勝手に変えずに相談して設計書も直す
- 上流で決めたことを、テストで確かめられる形で残す

## ポイント

- 開発は「要件定義 → 設計 → 実装 → テスト → 運用」の流れ
- V 字モデルで、設計とテストの対応を意識する
- ウォーターフォールは計画重視、アジャイルは変化への対応重視

### 問5【応用】

作る物が分からないまま実装を始めるより、先に必要なのは？

#### 選択肢

- A. 相談せず完成扱いにする
- B. 目的や必要な動作を確認する
- C. コード量を増やす
- D. 色だけを全て決める

#### 解答・解説

正解: B

何を実現したいかが分からないと、動く物ができても目的を満たせません。

## Option：完成条件を先に言葉にする

『できた』には実装、テスト、レビュー、運用手順など異なる意味が混ざります。チームで完成条件をそろえると、見積もりや引き渡しの誤解を減らせます。

**やってみよう：** パスワード再発行機能について、正常系だけでなく権限・期限・監査記録を含む完成条件を考えてみましょう。
