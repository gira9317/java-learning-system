## デザインパターンとは

設計でよく出会う問題と、その **定番の解き方** に名前を付けたものです。有名なのは、GoF（Gang of Four）がまとめた 23 のパターンです。

名前があることで、「ここは Strategy にしよう」と短く設計の意図を伝えられます。ただし、パターンを使うこと自体が目的ではありません。問題があるときに当てはめます。

## 分類

| 分類 | 目的 | 例 |
|---|---|---|
| 生成 | オブジェクトの作り方を工夫する | Singleton、Factory Method、Builder |
| 構造 | クラスやオブジェクトの組み合わせ方 | Adapter、Decorator、Facade |
| 振る舞い | オブジェクト間の役割分担 | Strategy、Observer、Template Method |

## よく使われるパターン

### Strategy（戦略）

処理の方法（アルゴリズム）を部品として差し替えられるようにします。条件分岐が増え続けるときに有効です。

```java
interface DiscountPolicy {
    int apply(int price);
}
class NoDiscount implements DiscountPolicy {
    public int apply(int price) { return price; }
}
class MemberDiscount implements DiscountPolicy {
    public int apply(int price) { return (int) (price * 0.9); }
}

class Cart {
    private final DiscountPolicy policy;
    Cart(DiscountPolicy policy) { this.policy = policy; }
    int total(int price) { return policy.apply(price); }
}
```

割引の種類が増えても、`Cart` を書き換えずにクラスを追加するだけで済みます。

### Singleton（シングルトン）

クラスのインスタンスを **1 つだけ** にします。設定情報など、全体で 1 つでよいものに使います。

```java
public class AppConfig {
    private static final AppConfig INSTANCE = new AppConfig();
    private AppConfig() {}                     // 外から new させない
    public static AppConfig getInstance() { return INSTANCE; }
}
```

便利ですが、どこからでも使えるため依存関係が見えにくくなり、テストもしにくくなります。乱用は避けます。

### Factory Method（ファクトリーメソッド）

インスタンスの作り方を、専用のメソッドに任せます。呼び出し側は、具体的なクラスを知らなくて済みます。

```java
static DiscountPolicy create(String memberType) {
    return switch (memberType) {
        case "member" -> new MemberDiscount();
        default -> new NoDiscount();
    };
}
```

### Builder（ビルダー）

引数の多いオブジェクトを、読みやすく組み立てます。

```java
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://example.com/api"))
        .header("Accept", "application/json")
        .GET()
        .build();
```

### Observer（オブザーバー）

あるオブジェクトの変化を、登録しておいた複数のオブジェクトに通知します。画面のボタンのクリックイベントなどがこの考え方です。

### Template Method（テンプレートメソッド）

処理の大まかな流れを親クラスで決め、細部を子クラスで実装します。

## パターンの土台にある原則

- **インターフェースに対してプログラムする**（具体的なクラスに依存しない）
- **継承より委譲（組み合わせ）**
- **変わるものと変わらないものを分ける**
- **拡張に対して開き、修正に対して閉じる**（開放閉鎖の原則）

## ポイント

- デザインパターンは、よくある設計問題の定番の解き方に付いた名前
- Strategy・Factory・Builder・Singleton・Observer はよく見かける
- 使うこと自体を目的にしない。問題があるときに当てはめる

> **確認しよう**
>
> - `if (type == A) ... else if (type == B) ...` が何か所にも増えてきたとき、どのパターンが役立つでしょうか。
> - Singleton を使いすぎると困ることを 2 つ挙げてみましょう。
